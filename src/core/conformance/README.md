# AAMVA Conformance Corpus

This directory holds test vectors that pin the generator's output to specific
byte strings. A change to the generator that produces a different encoding will
fail the conformance test (`src/tests/conformance.test.ts`), forcing an explicit
decision: either the change is wrong, or the vector needs to be regenerated and
the diff reviewed against the AAMVA spec.

## Provenance tiers

Every vector declares where its bytes came from. This matters more than it
sounds: a vector generated by our own encoder can only ever prove the encoder
has not _changed_, never that it is _correct_. Recording the difference is what
stops a regression baseline from being mistaken for evidence.

| Tier        | Source                                         | What a passing test proves                                                            |
| ----------- | ---------------------------------------------- | ------------------------------------------------------------------------------------- |
| `synthetic` | `scripts/gen-vectors.mjs` — our own encoder    | The encoder still produces what it produced before. Regression only.                  |
| `published` | AAMVA- or jurisdiction-published test material | The encoder matches that authoritative reference; scope is limited to the vector.     |
| `issued`    | A real credential, decoded and anonymised      | The encoder matches that observed layout; this does not certify an issuer or edition. |

Only `published` and `issued` count as evidence about the outside world. The
schema and the rules below are enforced by
`src/tests/conformanceProvenance.test.ts`.

Thirteen jurisdictions now have external reference layouts: AR, CT, FL, GA,
IL, KS, MO, NE, NY, PA, SC, VA, and WA. The 26 references comprise 21
unmodified source payloads, two anonymized issued layouts, and three
canonicalized layouts. The ratchet is 13/55. Forty-two jurisdictions still lack
a passing external fixture. Scope and source qualifications appear in the
[October 31 ledger](COVERAGE-2026-10-31.md).

Named variants live in `observed-profiles.json`, with separate source evidence
in `observed-profile-provenance.json`. Supply `encodingProfileId` to both schema
selection and generation. A retained imported source can identify its matching
profile in the UI; profile recognition does not establish issuer authenticity.
Strict mode still enforces the configured default edition. Historical and v12
standards tests use standard validation with strict mode disabled.

Connecticut
(`ct-v09-dl-issued.json`), decoded from an issued credential. It is the vector
that established that a payload can hold more than one subfile, that DAK is not
always space-filled, and that element order varies by issuer — three things
every other vector in this directory agreed on only because the same encoder
wrote them all. Its source was a field dump with uncertain trailing padding;
the fixture repairs the directory boundary and omits an empty ZCA element.
It is classified as a canonicalized derived layout, rather than an unmodified
source-payload match.

New York followed (`ny-v10-dl-issued.json`). Its byte layout took longer to pin
down: the card declares a 323-byte `DL` subfile whose unpadded elements account
for only 224, and a field dump cannot show where the rest went. The byte ledger
could — 100 bytes of space fill at widths that are mostly New York's own, and
one byte per subfile saved by closing the final element with the segment
terminator alone. Both are now in NY's encoding profile, and the vector
reproduces the card's directory exactly.

A second New York vector (`ny-v10-dl-issued-znb-fill.json`) comes from a card
whose `ZNB` fell one character short of its field. Its layout matches the first
card's byte for byte, and the one space of fill after `ZNB` is what showed that
New York pads that element to 90 as well. The first vector could not show it:
its placeholder fills all 90 characters, so it passes with or without the width.

## Vector format

Each vector is a JSON file under `vectors/`:

```json
{
  "id": "ca-v10-dl-baseline",
  "state": "CA",
  "version": "10",
  "subfileType": "DL",
  "description": "Synthetic regression baseline (no PII).",
  "provenance": {
    "tier": "synthetic",
    "source": "scripts/gen-vectors.mjs (this implementation's own output)",
    "capturedAt": null,
    "verifiedBy": null,
    "notes": "Regression baseline only. Not evidence of AAMVA conformance."
  },
  "input": { "DCS": "DOE", "DAC": "JANE", "...": "..." },
  "expectedBytes": "@\n<RS>\rANSI 636014..."
}
```

- **`input`**: the record passed to `generateAAMVAPayload`.
- **`expectedBytes`**: the exact wire-format string the generator must produce.
  Bytes match character-for-character including separators (`\n`, `\x1e`,
  `\r`).
- **`provenance.capturedAt`**: ISO `YYYY-MM-DD`, or `null` for synthetic
  vectors. Required for `published` and `issued` — without it there is no way
  to tell a current vector from a stale one.
- **`provenance.verifiedBy`**: who checked the bytes against the source.
  Required for `published` and `issued`.
- **`provenance.anonymization`**: required for `issued`; describes how PII was
  replaced.
- **`provenance.fidelity`**: required for external references. `unmodified-source`
  retains the recovered payload bytes; `anonymized` replaces identifying data;
  `canonicalized` records a derived layout with structural adjustments.

## Adding a new vector

### Synthetic (regression baseline)

Add an entry to `scripts/gen-vectors.mjs` and regenerate:

```bash
npx tsx scripts/gen-vectors.mjs
```

This captures the _current_ implementation's output as the new baseline. Use
synthetic vectors to lock in behavior that's already correct and prevent
accidental regressions.

### Published or issued (true conformance)

Real-world vectors are sourced from AAMVA-published test cards or actual
credentials. **Never check in real PII.** When adding one:

1. Decode the source barcode independently and inspect every field. Public marked specimens retain their original dummy bytes.
2. For authorized issued sources, replace PII (`DAA`, `DCS`, `DAC`, `DAD`, `DAG`, `DAI`, `DAQ`, `DCF`, `DBB`,
   `DBA`, `DBD`) with synthetic placeholders that **preserve byte length and
   character class** so the encoded output's byte layout is unchanged.
3. Hand-verify the resulting `expectedBytes` matches the decoded structure of
   the original (separators, padding, field ordering).
4. Fill in the full `provenance` block — tier, source, `capturedAt`,
   `verifiedBy`, and for `issued`, `anonymization`.
5. Raise `MIN_REAL_WORLD_JURISDICTIONS` in
   `src/tests/conformanceProvenance.test.ts` so the new coverage is locked in
   and cannot silently regress.

A failing real-world vector indicates the implementation diverges from what at
least one DMV actually issues — which is the highest-priority class of bug for
this project.

### When the source card disagrees with itself

Issued cards are not guaranteed to be internally consistent, and the CT vector
is the worked example: its header declares the DL subfile one byte longer than
the bytes it holds, which pushes the declared offset of the following `ZC`
subfile one past where `ZC` actually starts. The subfiles and the total length
are both right — only the boundary between them is wrong.

Record deviations like this in `provenance.notes` and keep the vector's
`expectedBytes` self-consistent. Reproducing an issuer's arithmetic error would
make our own directory unreadable to anything that checks it, and would pin a
bug in place under the name of conformance. The decoder absorbs a few bytes of
this drift when reading (see `readDirectory` in `core/decoder.ts`); the encoder
never emits it.

## Why this matters

Property-based and unit tests verify that the implementation is _internally
consistent_. Conformance vectors verify it matches _external reality_. Without
real-world vectors, "supports every jurisdiction" is plausibility, not proof —
and the coverage report exists so the size of that gap is a number rather than
an assumption.

For the related check that the _rendered symbol_ carries the bytes we think it
does — as opposed to our decoder agreeing with our encoder — see
`src/tests/scanOracle.test.ts`, which reads our barcodes back with ZXing.
